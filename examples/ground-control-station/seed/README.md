# GCS seed using maintained artifacts — TC-2402

From the repository root, with the normal Java/GraalVM prerequisites:

```sh
make gcs-seed-verify
```

This builds the current tools, compiles the checked-in YAML, resolves explicit pinned
imports, analyzes coverage/work/impact, renders reports and checks four failure/change
cases. To rerun with already-built tools:

```sh
python3 examples/ground-control-station/seed.py
```

The manifest is deliberately relative to the staged analysis root: `source/` paths
refer to copied inputs under `build/gcs-seed`. Edit this directory's authored sources,
not generated copies. Outputs are `build/gcs-seed/coverage.html`, `IMPACT.md`, `WORK.md`,
compiled artifacts, consumer-specific selections and `evidence.json`. Output source
links point to the retained staged snapshots. Rebuilding deletes only this example's
owned output directory. The workflow is also part of `make verify`.

## What the run establishes

Ten requirements describe the TC-2401 simulation boundary. Nine coverage assertions
connect them to three planned activities. GCS-EVIDENCE deliberately remains uncovered:
current planning tools cannot represent evidence adequacy or release authorization.
The analyzer returns a finding, while the demonstration script succeeds only if that
finding is actually present. No run, procedure execution or safety acceptance is claimed.

A GCS-STALE impact query reaches ACT-STATE, PLAN-GCS and the two addressing/dependent
work items. It does not change their Planned statuses. The check also:

- Rebuilds the source/compiled/report tree in a fresh temporary analysis root and
  compares generated bytes exactly.
- Changes the covered freshness threshold from 500 to 400 ms, retaining the baseline,
  and requires exactly GCS-STALE to become review-stale.
- Adds a nonexistent decomposition target and requires `dangling-reference`.
- Changes bytes behind a pinned import and requires `digest-mismatch`.
- Resolves every file link in the coverage HTML to a staged source snapshot.

The threshold mutation is a test of change detection, not a new accepted design limit.

## Observed limits and manual engineering work

| Need | Seed support | Remaining manual or future work |
| --- | --- | --- |
| Scenario meaning and operating limits | Requirement prose and descriptive scenario attributes | Scenario identity, typed context/mode references and checked allocations |
| Command/freshness contract | Required behavior in statements | Interface structure, units, timing semantics and compatibility checks |
| Power/link safety reasoning | Planned analysis activity | Hazard/control records, failure analysis and justified budget models |
| Exact selected artifact bytes | Explicit imports with SHA-256 pins | Named configuration/baseline manifests and designed/built/deployed comparison |
| Verification | Planned coverage and revision comparison | Reproducible procedures, execution, raw logs, result applicability and assessment |
| Work tracking | Typed addresses/dependencies and generated views | Corrective closure tied to accepted evidence and release decisions |
| Impact | Explained prospective reachability | Domain-specific semantic changes and evidence invalidation |
| Review | Source-linked reports | Human evidence-adequacy judgments, role assurance and scoped exceptions |

Consumer selections are intentionally different. The verification linker accepts
only requirement imports; work analysis reserves `work` for the selected local work
artifact. Impact accepts the explicit requirements/plan/work set. The script generates
three selections from the same pinned outputs and does not widen existing contracts.
There is no universal manifest that can be handed unchanged to every consumer today.

The seed is a runnable engineering-tool workflow, not a runnable vehicle simulator.
The synthetic autopilot and physical-system behavior remain future implementation.
See the [reference decision](../decisions/reference-system.md) for ownership and the
[project plan](../README.md) for the complete scenario ledger.

## Recorded acceptance

On 2026-09-07, `make gcs-seed-verify` passed in the working checkout and a fresh
source export with no copied binaries or dependency cache. Both compiled all six
required native tools and reproduced the seed observations above. The fresh output
root and the script's second temporary rebuild used only selected source snapshots.
The four negative/change checks and all report file links passed. This closes
TC-2402's current-tool demonstration; it does not close the deliberately uncovered
engineering obligation or execute vehicle behavior.
